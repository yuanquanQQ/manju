# AI 漫剧生成系统 V1：开发计划总览

## 1. 产品目标

将一本中文长篇小说（TXT、Markdown 或章节 JSON）转换为可播放的漫剧剧集，输出画面、镜头视频、对白配音、字幕、音效、配乐和最终 MP4。V1 以 Python 技术栈和自有 RTX 3090 24GB GPU 服务器为正式生成环境；开发机负责控制、审核和轻量测试，通过可配置的局域网接口访问服务器上的 LLM、ComfyUI 和 I2V 服务，数据不依赖公有云。

V1 的首要目标不是一次性处理整本小说，而是先稳定跑通一条可复现、可暂停、可恢复、可人工修订的端到端生产链路。

### V1 成功标准

- 选取连续 3–5 章，生成一集 3–5 分钟的完整样片。
- 任意阶段失败后可以从最近成功节点继续，不重复昂贵任务。
- 每个生成物都能追溯到小说章节、模型、工作流、提示词、参数和输入资产。
- 人物、服饰、场景和关键道具在同一集内保持可接受的一致性。
- 用户可以在 GUI 中审核并修改人物卡、分镜、提示词和候选素材。
- 完成样片后，再验证 100 章解析与 100 镜头批处理能力。

## 2. V1 范围

### 包含

- 小说导入、章节切分、结构化分析与实体归一。
- 可引用原文证据的世界知识库与混合检索。
- 人物、场景、道具和风格基准资产。
- 分集、场景、分镜和镜头脚本。
- 引擎无关的 Prompt DSL 与 ComfyUI 适配。
- 图片、图生视频、配音、字幕、音效、配乐和自动剪辑。
- PySide6 桌面端的项目管理、审核、任务控制与导出。

### 暂不包含

- 多用户协作、云端队列和分布式 GPU 调度。
- 自动训练大型基础模型。
- 无人工审核地生成整部长篇小说。
- 复杂角色口型驱动、专业级三维绑定和实时渲染。
- 商业素材版权采购；用户需自行确保模型、字体、音乐和素材许可。

## 3. 总体架构

```text
PySide6 GUI
    │
Application Service / Pipeline
    │  项目、任务、审核、重试、恢复
    ├───────────────┬────────────────┐
    │               │                │
Novel/KB Agents  Director/Prompt  Render/Compose
    │               │                │
    └───────────────┴────────────────┘
                    │
Data & Artifact Layer
SQLite + FTS5 + Vector Index + JSON Manifest + Files
                    │
Adapters
LLM / Embedding / ComfyUI / I2V / TTS / FFmpeg
```

边界原则：

- GUI 不直接操作模型、ComfyUI 或数据库，由应用服务统一调用。
- Agent 只完成受约束的推理任务，不负责文件管理和任务状态。
- Pipeline 负责任务依赖、幂等、重试、取消、恢复和进度。
- 数据库保存可查询状态，文件系统保存大对象，Manifest 保存可追溯元数据。
- 所有外部能力通过 Adapter 接入，避免业务逻辑绑定具体模型或 UI。

## 4. 跨阶段数据流

```text
原始小说
  → 标准章节与原文定位
  → 实体、事件、关系、状态变化
  → 世界状态与可检索知识
  → 角色/场景/道具资产
  → Episode → Scene → Shot
  → RenderSpec / Prompt
  → Shot Image → Shot Video
  → Voice / Subtitle / Music / SFX
  → Timeline → Episode MP4
```

每一步只消费上一阶段的稳定数据契约，不读取上一阶段的临时实现细节。

## 7. 全局工程约束

### 数据与版本

- 所有 Pydantic Schema 带 `schema_version`。
- 原始小说只读保存；LLM 结果、人工修订和发布快照分层存放。
- 数据库结构使用迁移工具管理，禁止通过删除数据库完成常规升级。
- 资产使用稳定 ID，不以可变化的人名或文件名作为唯一关联。
- 每次生成记录 `input_hash`、模型、模型版本、工作流版本、随机种子和参数。

### 任务状态

统一状态建议为：

```text
PENDING → RUNNING → SUCCEEDED
              ├──→ FAILED → RETRYING
              ├──→ PAUSED
              └──→ CANCELED
SUCCEEDED → STALE（上游输入变化）
```

任务必须幂等。相同输入与配置已成功时复用结果；上游人工修改后，只把受影响的下游节点标为 `STALE`。

### 质量门槛

- 技术成功与内容合格分开统计。HTTP 成功或文件存在不等于视觉合格。
- 自动检查负责格式、时长、尺寸、黑帧、静音、重复和缺失引用。
- 人工审核负责剧情、表演、构图、角色一致性和审美。
- 每个阶段保留固定基准集，修改模型或 Prompt 后做回归测试。

### 可观测性

- 每个任务有 `job_id`、结构化日志、耗时、重试次数和错误分类。
- 记录 GPU 峰值显存、生成速度、磁盘占用和缓存命中率。
- 日志不保存密钥；原文和生成内容默认只在本机。

## 8. 当前工程基线

阶段 01 已于 2026-07-23 按新版 Definition of Done 完成。阶段 02 正在执行：标准小说导入、严格 Schema、自然边界分块、逐字证据校验、显式失败、schema v2 持久化与增量任务复用已经完成；实体合并/拆分、人工评估集和 GPU 服务器实测尚未完成。

已识别的优先改进项：

1. 用 Pydantic/JSON Schema 校验 LLM 输出，而不是只检查字典字段。
2. 把“本章提及”与“全书首次出现”拆分；后者由实体归一和数据库状态判断。
3. 为事件、人物、场景保存原文证据、置信度和生成版本。
4. 强制重跑时采用可重复的 upsert/替换策略，避免重复或孤立数据。
5. 为开发机和 GPU 服务器分别提供环境诊断；当前开发机是 RTX 3060 Ti 8GB，正式生成服务器是 RTX 3090 24GB。
6. 在承担最终媒体合成的机器上安装或配置 FFmpeg/ffprobe；当前开发机环境诊断已正确报告二者缺失。

## 9. 开发顺序建议

先完成 M0，再用 3–5 章做端到端“薄切片”。薄切片跑通后回头扩大第二、三阶段的规模，最后才做整书批量生成。这样能尽早暴露数据契约、镜头成本、显存和一致性问题，避免在错误的数据模型上积累大量结果。
